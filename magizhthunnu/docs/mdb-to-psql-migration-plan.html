Section 1
Overview & Confirmed Decisions

magizhthunnu/CLAUDE.md leaves the database choice open ("Database: MongoDB or postgresSQL — use whichever is best for this app"). This document is the concrete plan for settling that: move all 7 Mongoose models used by the backend to PostgreSQL via Prisma. This is a planning document only — no source code has been changed.

Decisions confirmed for this plan:

• ORM: Prisma — TypeScript-first schema, first-class migration tooling.

• Data state: app is pre-launch, only seed data exists (3 users, 1 restaurant) → this is a clean schema rewrite + re-seed, not a live-data ETL / zero-downtime cutover.

• PostGIS will be available on the target Postgres host → used for the "restaurants near me" geospatial feature via geography(Point,4326) + GIST index.

Current stack

Node 22 + Express 4 + TypeScript, Mongoose 8.3.3 against MongoDB 7. Redis (ioredis) + BullMQ power caching and the email queue and are untouched by this migration. Frontend (React/Vite) is untouched — it talks to the API, not the DB, directly.

Scope

Everything under magizhthunnu/backend/src/{models,services,controllers,config} plus magizhthunnu/docker-compose.yml, magizhthunnu/backend/package.json, and magizhthunnu/backend/.env. No changes to frontend/, Redis, BullMQ, or sibling apps in the monorepo.

Section 1b
Login / Credential Continuity

There is no "username" field in this app. Login is email + password only — confirmed by grepping the entire backend (grep -rn "username" src/ returns zero matches). IUser, the login controller, and the Zod loginSchema all reference only email.

The 3 existing accounts are seed data only (admin/restaurant-owner/customer, created by backend/src/config/seed.ts). Since this migration is a clean re-seed rather than a data copy (Section 1), "same login" isn't automatic — it's guaranteed only because the new Postgres/Prisma path reproduces today's exact mechanics:

StepToday (Mongo)Post-migration (Postgres/Prisma) — must match
Password sourceseed.ts reads plaintext env vars (SEED_ADMIN_PASSWORD, etc., default test123) — no hardcoded hash anywhereSame env vars, same plaintext defaults — unchanged
HashingUser.model.ts pre('save') hook: bcrypt.hash(passwordHash, 12), only when modifiedPrisma $extends client extension must hash with the same bcrypt cost factor (12) on create/update — see mapping decision #12
Login lookupauth.service.ts: User.findOne({ email }).select('+passwordHash')prisma.user.findUnique({ where: { email }, omit: { passwordHash: false } }) — same field, same "hidden unless asked for" shape
Password compareuser.comparePassword(password) → bcrypt.compare(candidate, passwordHash)Exported comparePassword(candidate, hash) function, same bcrypt.compare call
Failure behaviorWrong email and wrong password both throw the same generic 401 INVALID_CREDENTIALS (no enumeration leak); deactivated account is a separate 403 checked after password succeedsPort unchanged — do not differentiate the error message between wrong-email and wrong-password

As long as Phase 2's auth.service.ts rewrite and Phase 5's seed-script rewrite reproduce this table row-for-row, all 3 seeded accounts log in with the exact same email/password after cutover. This is verified explicitly in the Phase 8 checklist (Section 5).

Pre-existing quirk, not a migration regression (see Risk #11): today's login does User.findOne({ email }) with no .toLowerCase()/.trim() on the input — Mongoose's lowercase:true only normalizes on write, not on query. It doesn't affect the 3 seed accounts (their emails are already lowercase constants), and the migration should carry this behavior over unchanged rather than silently "fixing" it.

Section 4
Mapping Decisions

Every Mongo/Mongoose-specific feature with no direct Postgres equivalent, and the call made for it.

#Mongo featureDecisionRationale
1ObjectId PKsUUID everywhereNo sequential-ID enumeration risk; opaque strings on both sides, no frontend assumptions break.
2User.addresses[] embeddedNormalized address table, FK cascade deleteAddresses are added/removed individually today — a real 1:N relation, not a snapshot.
3Cart.items[] / Order.items[] embeddedNormalized cart_item / order_line_item tablesItems are mutated one at a time (qty update, remove) — avoids rewriting a whole array per edit.
4MenuItem.customizations[].options[] (master data)Normalized menu_item_customization → _option tablesAdmin-managed list, edited option-by-option in the future admin UI.
5CartItem/OrderLineItem customizations (selected option snapshot)JSONBImmutable per-line snapshot, never queried independently — distinct from #4's master data.
6Restaurant.openingHours MapJSONB, not a tableFixed 7-key shape, always read/written whole — a join table would add cost for zero benefit.
7Payment.metadata (Mixed)JSONBDirect 1:1 — untyped by design on both sides.
8GeoJSON Point + 2dspheregeography(Point,4326) + GIST, via Unsupported(...)Closest match to Mongo's great-circle $near; forces access through $queryRaw since Prisma has no native GIS type.
9Text index + $text/textScoreGenerated tsvector column + GIN, queried via plainto_tsquery/ts_rankSame raw-SQL escape-hatch pattern as GIS — Prisma has no full-text-search API.
10TTL index (24h abandoned-cart expiry)Scheduled BullMQ repeatable job running deleteManyNo Postgres TTL equivalent; reuses BullMQ infra already in the stack instead of a new cron mechanism.
11Mongoose select:false fieldsPrisma Client global omit config, overridden per-query when neededClosest 1:1 behavioral match; safer than trusting every call site to remember an explicit select list.
12pre('save') bcrypt hook + comparePassword()Prisma $extends client extension + plain exported functionClosest analogue to Mongoose middleware — no call site can forget to hash. Must use the same bcrypt cost factor (12) and the same lookup shape (findUnique({where:{email}}, {omit:{passwordHash:false}})) as today's User.findOne({email}).select('+passwordHash'), so seeded-user login behavior is byte-for-byte preserved — see Section 1b.
13Order.paymentId ↔ Payment.orderId mutual refsDrop Order.paymentId; FK lives only on Payment.orderIdOrders are created before payments exist — a physical FK on Order would need nullable-then-backfill and a circular insert order.
14Money as plain NumberDecimal(10,2)Floats are unsafe for currency math; exact decimal arithmetic is essentially free in Postgres.
15Compound index over array field ({cuisineTypes,isOpen})Split: @@index([isOpen]) + @@index([cuisineTypes], type: Gin)Btree composite doesn't work over array columns; GIN is correct for array-containment (has/hasSome) queries.
Section 5
Migration Phases

Phase 0 Infra: Postgres + Prisma + PostGIS setup

  • docker-compose.yml: replace mongo:7 with postgis/postgis:16-3.4; env POSTGRES_USER/PASSWORD/DB; volume postgres-data; healthcheck pg_isready. Update backend service's env to set DATABASE_URL.
  • backend/.env.example / .env: MONGODB_URI → DATABASE_URL=postgresql://postgres:secret@localhost:5432/magizhthunnu?schema=public.
  • npm install @prisma/client && npm install -D prisma in backend/.
  • npx prisma init --datasource-provider postgresql → creates backend/prisma/schema.prisma.
  • Enable PostGIS via a versioned first migration (recommended) rather than a docker init script, so it travels with the schema.

Phase 1 Schema + migrations

  • Author schema.prisma per Section 3.
  • npx prisma migrate dev --name init --create-only to generate SQL without applying.
  • Hand-edit the generated migration SQL to add what Prisma can't express: CREATE EXTENSION IF NOT EXISTS postgis;, the generated search_vector column expression, CREATE INDEX ... USING GIST/GIN, and CHECK constraints (rating BETWEEN 1 AND 5, price >= 0, etc).
  • Apply: npx prisma migrate dev; generate client: npx prisma generate.

Phase 3 Geo / full-text / aggregation raw SQL helpers

New helper module (e.g. inline exports in restaurant.service.ts) using tagged-template $queryRaw — never $queryRawUnsafe with string interpolation:

export const findNearby = (lat, lng, radiusKm) =>
  prisma.$queryRaw`
    SELECT id, name, logo, rating,
           ST_Distance(location, ST_SetSRID(ST_MakePoint(${lng}, ${lat}), 4326)::geography) AS distance_m
    FROM restaurant
    WHERE ST_DWithin(location, ST_SetSRID(ST_MakePoint(${lng}, ${lat}), 4326)::geography, ${radiusKm * 1000})
      AND is_open = true AND is_verified = true
    ORDER BY distance_m LIMIT 20`;

export const searchRestaurants = (query) =>
  prisma.$queryRaw`
    SELECT id, name, description, rating,
           ts_rank(search_vector, plainto_tsquery('english', ${query})) AS rank
    FROM restaurant
    WHERE search_vector @@ plainto_tsquery('english', ${query}) AND is_verified = true
    ORDER BY rank DESC LIMIT 20`;

Rows return snake_case and untyped — add a small mapper to the camelCase DTO shape controllers already expect.

Section 7
Risks & Gotchas
1
Decimal JSON serializationPrisma.Decimal doesn't serialize to a plain number via JSON.stringify. Decide once, globally, whether the API returns money as strings or numbers.
2
Transaction semantics changeMaking the two flagged flows atomic is a correctness improvement, but callers now see all-or-nothing failure instead of any partial-success states they may have tolerated before.
3
Loss of Mongoose pre-save hooksThe bcrypt-hash hook's $extends replacement is new code needing focused unit tests (hash-on-create, hash-on-update-when-changed, no-op otherwise).
4
select:false → global omit is client-instance-scopedAny second PrismaClient instance (a one-off script, a stray test helper) not wired through the shared singleton will silently leak passwordHash/OTP fields. Enforce a single exported client.
5
Testing strategy changeTestcontainers needs Docker-in-Docker in CI; if unavailable, fall back to a shared compose Postgres + truncate-between-tests, which needs careful isolation.
6
Unsupported(...) columns are Prisma-Client-invisiblelocation/search_vector are maintained entirely via hand-written migration SQL — a future contributor unfamiliar with this pattern might "fix" it by removing the Unsupported declaration, causing the next migration to drop those columns.
7
Raw SQL bypasses camelCase mappingGeo/full-text helpers return snake_case rows; a forgotten mapping step leaks is_open/created_at-style keys into otherwise camelCase API responses.
8
Idempotency-key race in placeOrderEven inside a $transaction, findUnique-then-create isn't fully race-safe under READ COMMITTED. Rely on the unique constraint + catch P2002, not the pre-check.
9
Hand-written CHECK constraints invisible to schema.prismarating BETWEEN 1 AND 5 etc. are added by hand-editing migration SQL — document clearly so a future auto-generated migration doesn't silently drop them.
10
Stale existing docsdocs/system-design.html and Magizhthunnu_System_Design.pdf describe the Mongo-era LLD and will mislead readers until regenerated (out of scope here).
11
Email lookup is case-sensitive on read, not just on writeMongoose's lowercase:true only normalizes email on save; login/register both query with the raw, unnormalized input email. Pre-existing in the current Mongo app, not introduced by this migration — carries over unchanged. Doesn't affect the 3 seed accounts (already lowercase), but a future mixed-case login report shouldn't be blamed on the DB migration. See Section 1b.
